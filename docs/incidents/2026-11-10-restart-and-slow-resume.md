# 2026-11-10: A restart stopped the long jobs, and the resume was slow

Cause: the development machine was restarted from the Windows menu at 23:15, which ended the detached backfill and the two jobs waiting on it (the earlier lid close of 03:14 had done the same). On relaunch, the resume script first ran `ofs clean-temp`; walking about a million partition files took more than 30 minutes, while holding the data lock that the backfill needs, so nothing downloaded during that time.

Fix: the resume script relaunches the jobs immediately; leftover `*.tmp-*` and `*.part` files are harmless (no reader matches them: every table is read through `*.parquet`) and are cleaned later with `ofs clean-temp` when no job is writing. Finished days and simulation cells are skipped on resume, so the restart cost about an hour of downloads and nothing else. Operations: on the production VM the jobs run in containers with `restart: unless-stopped`; a laptop must not be restarted or closed during a backfill.

Second occurrence: on 2026-11-11 at 04:42, after Windows had installed an update during the night, the machine was restarted again from the Start menu; the jobs stopped for eight hours until the next check. The relaunched backfill then spent about a minute per finished week just to skip it: each (pair, market) group read its 84-day seasonal profile before finding that every day was already reduced. `process_group` now reads the profile only when a day still needs pass 2, which turns the skip into a few file-existence checks. Operations: pause Windows Update while long jobs run.

Third occurrence: on 2026-11-11 at 16:23, without any restart, every job process (the backfill, its `ofs` worker and the two waiting runners) ended in the same second, with no error in their logs. The event logs show a heavy interactive program starting on the machine three minutes earlier, and the same sequence on 2026-11-10 at 21:53 followed by the backfill stopping at 22:00 (that stop had been attributed to the 23:15 restart, which only found it already dead). Whether the processes were ended by hand or by that program is not established. The jobs now start at below-normal priority, which their child processes inherit, so an interactive program keeps the CPU it needs; resume costs a few minutes since the skip fix.

Fourth occurrence: on 2026-11-12 at 11:20, with no restart and no game client running, both job trees then running ended within two seconds (the simulation study and the reduction of the volume-centred statistics, runners included). The reduction's `ofs` process reported exit code 0xC000013A, which is a console control event (Ctrl+C, close). Its runner was set to ignore Ctrl+C and still ended right after it, so the consoles were most likely closed: a close event cannot be ignored. Three idle test processes, started the same way the day before with consoles of their own, were not touched. Twenty-four seconds later the user cancelled a scheduled defragmentation of the data disk, which had been slowing the reduction. The fix removes the consoles altogether: the runners now start under `pythonw.exe` (no console) and launch `ofs` with `CREATE_NO_WINDOW` (a hidden console its pool workers inherit). There is then no window to close, and no console event can reach a job. Finished cells and days were skipped on resume, so the stop cost about 30 minutes.

Fifth occurrence: on 2026-11-12 at 23:02 and on 2026-11-13 at 13:01 the laptop was shut down while the development estimates were running. Estimates were written only once every pair was done, so each shutdown lost the whole run. Each restart then spent close to two hours before its first pair, reading the realised variance of every pair to classify the volatility regimes: 43,000 small files on a cold hard disk. `run_estimates` now saves each pair-market as soon as it is computed, and the regimes with them, in a folder named after everything the results depend on (sample, days, replications, configuration, code version). A restarted run reads them back and computes only what is missing, so a shutdown costs the pairs in flight, about fifteen minutes. Operations: a commit, or a change to a tracked file, changes the code version and makes a restarted run start over, so the repository is left untouched while an estimation runs; work in progress goes to a separate worktree.

Cause of the third and fourth occurrences, found on 2026-11-14: the antivirus. Avast's Do Not Disturb mode (its log calls it game mode) starts whenever a full-screen program comes to the front, which includes the code editor and media players, and applies a rule named `PauseSystemBackgroundTasks`. Its log shows that rule being switched on or off in the same minute as every unexplained stop (2026-11-10 22:00, 2026-11-11 16:23 and 16:29), and two seconds after the one timed to the second (2026-11-12 11:20:30). The same rule disables scheduled tasks while it is active, which is why the logon task that relaunches the jobs was found disabled three times. How the rule ends console processes is not established; the jobs have run without a console since 2026-11-12 and have survived every activation since. Operations: switch that mode off on a machine that runs long jobs, and check the state of the relaunch task when checking the jobs.

Tests added: tests/unit/test_registry_run.py::test_run_estimates_resumes_from_checkpoints (a stopped run resumes without recomputing a saved pair or re-reading the regimes); the reader side of temporary files is covered by tests/unit/test_misc.py::test_only_temporary_files_are_cleaned.
