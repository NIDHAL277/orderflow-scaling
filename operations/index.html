    Operations¶

    One virtual machine is enough: the pipeline runs once a day, updates the rolling estimates and the dashboard. Target cost 0–5 € a month.

    Component Choice Note
    Machine Oracle Cloud "Always Free", Arm Ampere A1 size for 2 cores / 12 GB; check the current free quota first
    Backups Cloudflare R2 via rclone scripts/backup.sh, weekly
    Monitoring Healthchecks.io ping each day; alert when missing
    HTTPS Caddy reverse proxy automatic certificates, rate limit module

    Alternative: a laptop left on at night with the same docker-compose.yml.

    Deploy¶

    Step by step on Oracle Cloud, with the set-up script of the machine (scripts/vm-setup.sh): Deploying on Oracle Cloud. In short:

    git clone https://github.com/NIDHAL277/orderflow-scaling && cd orderflow-scaling
cp .env.example .env            # Healthchecks URL, hostnames, R2 credentials
mkdir -p data && sudo chown 1000 data
docker compose pull && docker compose up -d
docker compose exec pipeline ofs status

    Building behind a TLS-inspecting proxy or antivirus (one that re-signs HTTPS with its own root, such as Avast's "Web/Mail Shield"): the build's downloads fail with curl: (60) unable to get local issuer certificate. Export that root certificate as PEM and pass it as a build secret, which only the local image then trusts: docker build --secret id=extra_ca,src=root.pem -t orderflow-scaling:local . The proxy image takes the same secret: docker build -f docker/caddy.Dockerfile --secret id=extra_ca,src=root.pem -t ofs-caddy .

    Rehearsing the CI job before a push, when developing on Windows or macOS: the workflow runs on Linux, where some things differ (worker processes are forked, not spawned; file names are case-sensitive). scripts/ci-rehearsal.sh runs the same steps in a container started from the local image, on a git bundle of the repository; its header gives the two commands. It found the hang described in an incident note.

    Daily run (ofs daily, cron 30 2-12 * * *)¶

    1. 02:30 UTC: download yesterday's files; if absent, exit code 75 and retry every hour. Each run also replays the six days before (late files, failed downloads).
    2. Validation, reduction, update of the daily statistics. After Sunday's data, the files Binance re-published over the last 30 days are applied (ofs recheck), then the months that no run can change any more are folded into one file per statistic, pair and month (see "Monthly packs" below).
    3. Rolling 24-month estimates (confirmatory tests stay frozen on the frozen sample), then the live forecasts of every pair for the next 1, 5 and 22 days (data/forecast/live/{day}.parquet) and the live track record of past forecasts whose target is now complete (data/forecast/live_scored.parquet). Both need the protocol to allow the rolling estimates; a failure sets live_forecasts: false in the status and sends a fail ping, the data of the day being already saved. On the weekly recheck day, the change-point monitor of H0 runs too; pairs with an alarm in the latest block are listed in the status (changepoint_alarms) without failing the run.
    4. Healthchecks.io ping on success, fail ping otherwise (and at 12:xx UTC for files still absent, which become "missing").
    5. Sunday 04:00: backup of every derived table to R2 (scripts/backup.sh: daily statistics, estimates, tests, forecasts, manifest, validation, simulation, status, data quality, regime monitor, comparison of venues).

    Exit codes: 0 done (later runs of the same day are no-ops), 75 waiting for Binance or another command writing the data, 1 failure.

    Health (ofs status, GET /health, the dashboard) has three states. degraded: the last run reported a problem (blocked days, files still missing at 12:00 UTC, disk above 80 %, live forecasts failed); it comes first. stale: no problem reported, but the last verified day is more than 3 days old; Binance publishes a day later and the run retries until 12:30 UTC, so one or two days is normal, and older means that a run was missed or that the machine is stopped. ok otherwise. The age of the last verified day is always reported (data_lag_days).

    One writer at a time: every command that writes the shared data (ingest, backfill, reduce, validate, recheck, history, estimate, test, daily, clean-temp) holds the operating-system lock data/status/pipeline.lock; a second writer exits at once with code 75 (cron retries it the next hour). The lock belongs to the open file, so a killed process never leaves it behind. status, quality, the API and the dashboard only read and never wait.

    L2 collector (optional, always on)¶

    docker compose --profile l2 up -d collector starts ofs collect-l2 for BTCUSDT, ETHUSDT and SOLUSDT (1-second books, 20 levels, every trade) into data/l2/. It takes no pipeline lock. Its status event every minute counts messages, snapshots, resyncs and reconnects; a growing resync count means a lossy network. See L2 collector.

    Backfill and data quality (O1)¶

    ofs backfill --from 2024-11-01 --to 2026-10-31 --jobs 3   # resumable: done days are skipped
ofs quality  --from 2024-11-01 --to 2026-10-31            # exit 1 while O1 is not met

    The backfill downloads chunk k+1 while chunk k is validated and reduced, and deletes each raw file once reduced, so at most two chunks (a few GB) of raw files are on disk. It is limited by bandwidth. Measured on 2026-11-09: 2024-11-01 for the 60 pairs and their perpetuals was 0.3 GB (volatile days are larger: the BTCUSDT perpetual alone was 46 MB on 2025-03-10), the connection gave 3.1 MB/s with 1 or 6 parallel downloads, and the day was reduced in 35 s with 4 processes. Reduced outputs take about 60 MB a day.

    ofs quality writes data/quality/day_states.parquet (one row per pair, market and day) and data/quality/quality.parquet (days per state and coverage per pair). Every day of the window ends reduced, blocked (validation), or without a file: not_listed, delisted or suspended are explained; unexplained, not_reduced and not_attempted are not, and O1 requires none of them.

    Monthly packs¶

    The reduction writes one small file per statistic, pair and day; two years make about a million files, which a hard disk opens slowly and a backup uploads one by one. Once a month is out of reach of the daily replay and of the weekly recheck (35 days after its end), its per-day files are folded into one file per statistic, pair and month, {YYYY-MM}__pack.parquet (ADR 0016). The weekly run does it for the months that just closed; ofs compact does it for every closed month (resumable, holds the pipeline lock). Readers see the same rows either way; a day recomputed later (manual backfill, version bump) gets a per-day file that takes precedence until the next compaction folds it in.

    Results snapshot¶

    ofs snapshot export                 # -> results-snapshot.zip (about 120 MB)
ofs snapshot fetch                  # latest release -> snapshot/ (or --source URL-or-file)
OFS_DATA_DIR=snapshot uv run streamlit run dashboards/app.py

    The snapshot holds the tables the dashboard and the API read: tests, estimates without the bootstrap replicates, forecasts, simulation summaries, data quality, regime monitor, comparison of venues, manifest and status, with a manifest of sizes and SHA-256 checksums (snapshot.json). It holds no raw Binance file and no daily statistics. Attached to a release, it lets anyone browse the results without running the pipeline. fetch refuses unsafe paths, unlisted or missing files and checksum mismatches before it writes anything, and never overwrites a pipeline data directory. The dashboard recognises a snapshot and says so, instead of judging a pipeline that does not run there.

    Incidents¶

    Incident Detection Action
    Daily file absent at 12:00 UTC status missing in the manifest replayed automatically by the next six daily runs; older gaps: ofs backfill --from D --to D; the dashboard shows the gap
    Wrong checksum M1 new download; two failures alert
    Binance format change M2 schema failure alert, fix the loader, add a regression test, replay
    Disk full alert at 80 % purge data/raw/, check deletion after reduction
    No run for days (machine stopped, cron down) health stale, data_lag_days above 3; no Healthchecks ping restart the stack; ofs backfill --from D --to D for days older than the six the daily run replays, then ofs daily
    Interrupted run (kill, reboot) *.tmp-* / *.part files ofs clean-temp --dry-run, then ofs clean-temp; rerun the command: done days are skipped
    Live forecasts failed status live_forecasts: false, fail ping read the live_forecasts_failed event in the log; the next daily run retries; a missing day of forecasts stays missing (forecasts are never made after the fact)
    Regression after deployment tests or dashboard OFS_IMAGE_TAG=<previous> docker compose up -d

    Every real incident gets a three-line note in docs/incidents/: cause, fix, test added.
